# 资金流水工具套件
## FundsAnalysis

面向资金流水走向分析的桌面工具套件：把「原始账单 → 清洗 → 合并 → 总表/透视表 → 资金流向图与分析报告」
串成一条可接力的流水线。五个功能各自独立可用、互不干扰，产物按固定命名落在同一个输出目录，
下一步会自动读取。

当前版本：**v2.0.5**（版本变更见 [TODO.md](TODO.md) 的版本小节；结构与设计说明见 [工具套件合并方案.md](工具套件合并方案.md)）

## 功能一览

| 功能 | 输入 | 产物 |
| --- | --- | --- |
| **A 导入与清洗（微信）** | 微信账单 `TenpayTrades.txt`（或所在文件夹，支持单文件含多段账单） | `01_统一流水.tsv`、`01_清洗报告.txt` |
| **A 导入与清洗（支付宝）** | 支付宝「账户明细」导出的 csv（或所在文件夹） | `01_统一流水_支付宝.tsv`、`01_清洗报告_支付宝.txt` |
| **B 多来源合并** | 一份或多份统一格式流水 | `02_合并流水.tsv`、`02_合并说明.txt` |
| **C 流水总表与透视表** | 统一格式流水 | `03_流水总表.xlsx`、`03_流水总表.csv`、`03_数据透视表.xlsx` |
| **D 资金流向分析** | C 的 `03_数据透视表.xlsx`（汇总件，**推荐**：`数据透视表` 表就是边数据）或统一格式流水 | `04_资金流向图与流水分析报告.html` |

主界面按 **微信流水导入 → 支付宝流水导入 → 多来源合并 → 流水总表与数据透视表生成 → 资金流向分析图和报告生成** 排列。
微信与支付宝两份产物列结构完全一致（同一组列、同一顺序、`来源` 列区分），可直接交给功能 B 一起合并。

`03_数据透视表.xlsx` 含三张表：

- **数据透视表**：`用户方 | 用户侧角色 | 支出/收入 | 客户方 | 对手侧角色 | 求和项:金额(元) | 笔数`，
  其中两个「角色」列是 `=VLOOKUP(A2,人物关系图!B:C,2,0)`（对手侧指向 D 列）公式，角色由
  **人物关系图** 表决定，可在 Excel 里直接按角色筛选与做数据透视。
- **按主体汇总**：每个主体的支出、收入、净流入，按净流入降序。
- **人物关系图**：只有表头 `序号 | 姓名 | 角色`，**留空由人工填写**（姓名写成与流水一致的名字即可，
  数据透视表的角色列会自动带出；工作簿已设置打开时重算公式）。

功能 D 可以直接读 `03_数据透视表.xlsx`（**推荐用法**）：透视表的「数据透视表」表本身就是
`用户方 ↔ 客户方` 的合计金额与笔数，程序按列名识别后直接构图，不需要逐笔时间。
选到汇总件后点 **「载入「人物关系图」人物」** 可一次把表里已填的姓名带入名单，
默认口径是 **只看名单内双方的往来**（用户方和客户方都要在名单里）——几万行的汇总表立刻缩成
「关注的人之间」的窄图（实测 10,195 行汇总 → 20 人名单 → 67 行 / 19 主体 / 20 通道，0.4 s，HTML 约 0.07 MB；
同一名单放宽为「含名单外直接对手」则为 8,481 行 / 5,634 主体 / 1.0 s / HTML 约 1.7 MB）。
也可以不筛选直接全量出图，或选逐笔明细（`03_流水总表.xlsx` / `02_合并流水.tsv` / `01_统一流水.tsv`）保留时间维度。

## 运行

```
python main.py          # 图形入口：五个功能卡片
```

依赖见 `requirements.txt`（pandas / networkx / openpyxl / xlrd）。Win10+ 用 Python 3.13 即可；
Win7 需 Python 3.8.10 + 兼容依赖组合（见合并方案 §6.5）。

打包成单文件 exe：双击 `PackTool/PackWin.bat`，按提示选版本（详见 `PackTool/打包说明.txt`）。

| 选项 | 用哪套 Python | 依赖 | 产物（都在 `PackTool/dist/`） |
| --- | --- | --- | --- |
| `1` → Windows 10/11 版 | 本机 Python 3.9+（推荐 3.13） | 项目根 `requirements.txt`（pandas 3.0.3 / networkx 3.6.1 / openpyxl 3.1.5 / pyinstaller 6.21.0） | `资金流水工具套件Windows10以上v<版本>.exe` |
| `2` → Windows 7 兼容版 | **必须 Python 3.8.10**（3.9 起不再支持 Win7） | `PackTool/requirements_win7.txt`（pandas 2.0.3 / networkx 3.1 / openpyxl 3.1.2 / pyinstaller 5.13.2） | `资金流水工具套件WIN7版v<版本>.exe` |

一个脚本管两条线（v2.0.4 起合并，原先的 `PackWin10.bat` / `PackWin7.bat` 已废弃），
流程是「临时 venv → 装依赖 → PyInstaller 打包 → 自动校验 → 自动删 venv」，
exe 名字里的版本号自动取自 `core/__init__.py`；图标与「软件信息」放在 `PackTool/PackInfo/`
（`icon.ico`、`version.txt`——两个版本共用一份，字段沿用 1.3.2：
公司 `wulvxinchen`、`github.com@drpasserby`、版权 `Copyright © 2026 wulvxinchen.cn`）。
两版 exe 功能完全一致，Win7 版也能在 Win10/11 上跑，实测慢约 25%（功能 C）/ 37%（功能 D），
详见 `PackTool/打包说明.txt` 第五节。
`PackTool/PackWin.bat` 存的是 **ANSI/GBK** 编码——cmd 解析 UTF-8 的中文行会按字节截断并报
`'xxx' is not recognized`，以后改脚本里的中文提示请另存为 ANSI，不要存 UTF-8。
打包命令里有两处是**硬要求**，缺一个 exe 就会报 `ModuleNotFoundError`：
① `set "PYTHONPATH=%CD%\.."`——`--collect-submodules` 是靠 `sys.path` 枚举子模块的，
只写 `--paths ".."` 实测会收集成空列表（exe 里只剩一半 core/ui 模块）；
② `--collect-submodules core ui tools`——主界面是按注册表动态 import 功能模块的，
静态分析扫不到这三行里的模块。脚本打完会自动用 `archive_viewer` 校验 exe 里有没有
`tools.flow.tool` / `tools.alipay.tool`，缺了就直接报错停下。

## 数据格式契约

统一格式的**列顺序固定**（下表自左向右即产物顺序；v2.0.3 起按用户指定顺序排列）：

```
用户ID | 用户方 | 支出/收入 | 对手方ID | 客户方 | 金额（元） | 交易时间 | 订单号 | 来源
交易类型 | 交易业务类型 | 交易状态 | 说明 | 对手方接收金额 | 对手侧银行名称
```

读取一律**按列名**认列（`core/schema.py` 的 `COL_*` 常量），不再依赖列位；
只有 1.3.2 的历史文件（前 4 列 = 用户方 | 支出/收入 | 客户方 | 金额）才由 `normalize()` 按列位兜底兼容。

中间格式统一为 `.tsv`（utf-8-sig，制表符分隔）；功能 C 另外额外交付 `.xlsx` 与 `.csv`。

扩展列**按需写入**，且**整批全空的扩展列会自动省略**（例如财付通账单里没有「交易状态」）：
功能 A 界面上的「选择需要写入的列…」可以只勾选需要的扩展列（`用户ID` / `对手方ID` 两个账号列
与 4 个必需列始终保留、界面上勾选框为锁定状态），不改动账单原始文件；
勾掉或省略的列不会进入统一流水，后面的总表与流向图自然也不会带上——**没选 / 没有的列直接不写出，
其余列的相对顺序不变**。
两个账号列即使整批为空也不省略——微信与支付宝就是靠它们占同一组列，
少一列就会让合并后的总表在两边「对不上号」。
（1.3.2 的「原始文件」列已去掉：一批账单本来就都是同一个导出文件名，留着没有信息量。）

各扩展列的来历：

| 统一列 | 微信/财付通来源 | 说明 |
| --- | --- | --- |
| 用户ID | 用户ID（或 用户侧账号ID）；支付宝：`用户信息` 原文 | 账号**原始标识**（强制列），微信取账号 ID、支付宝取 `2088…(姓名)` 原文，便于回查原始账号；同一来源内可精确定位，**跨来源因 ID 体系不同不会自动匹配**（微信 `wxid_…` 与支付宝 `2088…` 是两套编号），跨来源同人仍按姓名对齐；姓名由「用户方」承载 |
| 对手方ID | 对手方ID（或 对手侧账号ID）；支付宝：`交易对方信息` 原文 | 同上，对应「客户方」 |
| 交易时间 | 交易时间 | 原样保留 |
| 交易类型 | 交易类型 → 交易用途类型 → 交易业务类型 | 取第一个存在的列；真实财付通账单取到「交易用途类型」（转账/消费/提现/退款…） |
| 交易业务类型 | 交易业务类型 | 支付渠道：快捷支付 / 余额支付 / 其它支付 |
| 交易状态 | 当前状态 | 微信支付账单有，财付通账单没有 → 自动省略 |
| 说明 | 备注1 + 备注2（或 交易备注 + 商品） | 两段都有时用「；」连接；不可见字符会被清掉 |
| 订单号 | 交易单号 | 去重用 |
| 对手方接收金额 | 对手方接收金额(分) ÷ 100 | 对方实际到账金额，仅部分「出」方向记录有值，可用于对账 |
| 对手侧银行名称 | 对手侧银行名称 | 对手方开户行 |
| 来源 | — | 功能 B 合并时标记数据来自哪份流水（微信/支付宝/文件名） |

## 输出与接力

- 默认输出到**输入文件所在目录**下的 `输出_时间戳/`（重名自动加 `_2`），界面里可改。
- 产物命名固定（见上表），同一目录内 `session.json` 记录每一步的产物与参数，下一步自动读取；
  同名产物写出前会自动备份为 `.bak`。
- `运行日志.txt` 与产物同目录：终端与文件双写，打包成 `--noconsole` 后仍可排障。

## 清洗规则

| 规则 | 内容 | P0 状态 |
| --- | --- | --- |
| R1 | 自转自（用户方 = 客户方）去除 | 已实现（默认开，可关） |
| R2 | 非「支出/收入」记录去除（方向取值兼容 `支出/支/出/借` 与 `收入/收/入/贷`；支付宝的「收/支=其它」也在此过滤） | 已实现 |
| R3 | 无效状态记录去除 | P1 |
| R4 | 非转账类流水去除（默认关，三档：不过滤 / 只保留转账类 / 只保留对外转账） | 已实现 |
| R5 | 去重（订单号优先，其次 时间+金额+双方+方向） | 已实现（默认关，可开） |
| R6 | 单位统一：微信「交易金额(分)」→ 元，附金额对账（支付宝「金额（元）」本就是元，不再换算） | 已实现 |
| R7 | 空值 / 非正金额去除 | 已实现 |
| R8 | 表头定位与尾部说明截断 | 已实现 |

> R5 说明：同一笔交易在支出方与收入方视角下订单号相同，判重时按「订单号 + 用户方 + 方向」
> 组合判定，避免把应当保留的对手记录当成重复删掉。

> R4 说明：三档分别是——「不过滤（保留全部记录）」（默认）、「只保留转账类」（按 `交易用途类型` 判定，
> 实测会去掉 提现/消费/退款/手续费 等）、「只保留对外转账」（在上一档基础上再去掉零钱通申购/赎回这类理财申赎）。
> 若账单里没有可用的用途列，则只在报告里提示、不做过滤（不会把数据误杀成空）。

## 清洗报告（`01_清洗报告.txt` / 支付宝为 `01_清洗报告_支付宝.txt`）

每次功能 A 运行都会写一份，共七节：① 输入文件清单；② 清洗结果（每条规则过滤了多少行、R4 档位与判定列）；
③ 金额与单位换算对账（分 → 元；另列「清洗后、去重前」的合计，避免把 R5 去重误判成单位错误）；
④ 关键字段取值分布（借贷类型 / 交易用途类型 / 交易业务类型 / 对手侧银行 top8；支付宝版为 收/支 / 消费名称 / 支付方式 / 交易来源地）；
⑤ 微信版为「对手方接收金额对账」，支付宝版为「被 R2 过滤掉的「其它」方向构成」；
⑥ 写入字段与格式说明（写入列、自动省略的空列、人工勾选列、不可见字符清洗）；
⑦ 说明与局限。若整批数据被规则过滤干净，这份报告会**先写出来再报错**，是排查格式问题的唯一线索。
第二节末尾还有一节「**被删样例**」：每条规则列出前 5 条被删记录（形如
`2024-01-05 10:00:00 | 张三 → 张三 | 支出 | 20.00 元`），便于人工复核「是不是误杀了正常流水」——
规则口径有疑问时先看这里，再决定要不要调整勾选。<br>
功能 B 另写一份 `02_合并说明.txt`：输入文件清单、来源分布、去重前后行数，
以及**订单号一致性检查**（同一订单号两侧金额不一致 / 同向重复 / 主体对不上各多少组，列前 10 组明细）。

## 微信账单支持范围（功能 A）

- **两种导出格式**：财付通账单（方向列 `借贷类型` 取值为 `出` / `入`）与微信支付账单
  （取值为 `支出` / `收入`）；两种都按同一套规则清洗，落成统一格式。
- **多段账单**：一个 txt 里若拼接了多份账单（含重复表头），会自动识别并跳过重复表头行，
  不会把表头当成数据行。
- **扩展列别名**：不同导出的备注/类型列名不同，按 交易类型→交易用途类型→交易业务类型、
  交易备注→备注1、商品→备注2 的顺序取名，取不到就留空。
- **不可见字符**：真实财付通账单的「备注2」每一行都以 `\u200c\u200e\u202a\u202c` 这类不可见字符开头
  （去掉后 17 万行里有约 12 万行其实是空的）。所有文本列在读写时都会清掉这类字符，避免「说明」列被污染、
  也避免空值判断失效。
- **整批为空列自动省略**：某份账单没有的扩展列（如财付通账单没有「交易状态」、没有「对手方接收金额(分)」）
  不会在产物里留一列空白，报告里会写明省略了哪几列。
- **对手方接收金额对账**：有该字段的记录（真实数据里占「出」方向的 32.8%）会与「交易金额」比对，
  不一致的会在报告里列出构成（实测绝大多数是微信红包的发放额与领取额不同、以及零钱通代销渠道的记账口径差异），
  入表金额一律以「交易金额」为准。
- **只有表头的文件**：记为「无数据行，已跳过」，不影响同一批中的有效账单。
- **全部被过滤时**：不会只丢一句「没有可用的有效数据」，而是先写出 `01_清洗报告.txt`，
  逐条列出 R1/R2/R4/R5/R7 各过滤了多少行、实际读到的借贷类型与用途取值 top8、以及报告路径，
  便于判断是格式不支持还是数据本身如此。
- 一批里成功解析多个文件时，导入窗口会**自动勾选 R5（去重）**并提示「多文件可能重复计入」；不想去重可手动取消。
- **列选择**：界面可勾选要写入的扩展列（4 个必需列 + `用户ID` / `对手方ID` 两个账号列固定保留、勾选框锁定），默认全选；产物列顺序固定（用户ID | 用户方 | 支出/收入 | 对手方ID | 客户方 | 金额 | 交易时间 | 订单号 | 来源 | 其他信息）。
- **真实账单实测**（97 个文件 / 171,214 行，方向 `出` 58,460 / `入` 27,147）：清洗后保留 64,310 行，
  用途分布 转账 105,822 / 消费 22,810 / 退款 2,124 / 手续费 128 / 提现 8，
  支付渠道 快捷支付 86,178 / 余额支付 44,104 / 其它支付 610。
- **强制账号列实测**（用户提供的 `处理` 目录：96 个微信账单 + 2 份支付宝账户明细）：
  微信原始 85,607 行 → 入表 64,310 行（去重 1,136）、5,432 个主体，`用户ID` / `对手方ID` 非空率均 100%；
  支付宝 8,739 → 8,057 行、1,438 个主体，`用户ID` 100% / `对手方ID` 99.9%；
  合并后 72,367 行、15 列契约齐全（其中 112 组同一订单号自相矛盾，见 `02_合并说明.txt`）。

## 支付宝账户明细支持范围（功能 A）

- **识别方式**：文件夹递归找 `.csv`，按文件名含「账户明细」或表头含「交易号」「用户信息」判定；
  不是这个格式的文件会被跳过，不会当成账单硬解析。
- **编码与分隔符**：自动识别 `GBK` / `UTF-8`（含 BOM），逗号分隔，表头固定 17 列；
  字段值常带前导制表符（如 `"　2088…(许文仙)"`），读写时会清掉。
- **列映射**（原始 17 列 → 统一格式）：

  | 统一格式 | 支付宝来源列 |
  | --- | --- |
  | 用户方 / 客户方 | `用户信息` / `交易对方信息`，统一取括号内姓名（`2088122934548576(许文仙)` → `许文仙`；无括号的 `花呗` 原样保留） |
  | 用户ID / 对手方ID | `用户信息` / `交易对方信息` 的**原文**（如 `2088122934548576(许文仙)`、`花呗`），与微信侧两列占同一组列；两套编号体系不同，跨来源同一人仍按姓名对齐 |
  | 交易时间 | `交易创建时间` |
  | 交易类型 | `类型`（即时到账交易 / 支付宝担保交易 / 纯预订交易 …） |
  | 交易业务类型 | `支付方式`（余额 / 余额宝 / 中国建设银行(4904) …） |
  | 交易状态 | `交易状态`（交易成功 / 还款失败 …，失败流水默认保留） |
  | 说明 | `消费名称`；`备注` 与它不同且非空时以「；」拼接（相同则不重复拼接） |
  | 订单号 | `交易号` |
  | 来源 | 固定写 `支付宝` |
  | 对手方接收金额 / 对手侧银行名称 | 支付宝没有这两个字段 → 整列为空，按「空列自动省略」不写入产物 |

- **不入表的列**：`对应的协查数据`（身份证号）、`商户订单号`、`付款时间`、`清算流水号`、`交易来源地`
  等敏感或口径重复的列不写入产物；报告里只提示有多少行带身份证号。
- **「收/支=其它」**：真实样本里 225 行全部是「余额宝-自动转入 / 余额宝-转出到余额」且对手方就是本人，
  属于自账户划转，按 R2 过滤（报告第五节列出构成）。
- **R4 判定列**：支付宝没有财付通的「交易用途类型」列，改按 `消费名称` 是否含「转账」判定；
  「只保留对外转账」一档会再去掉 余额宝 / 余利宝 / 小荷包 / 自动转入 / 自动攒 等理财申赎关键词。
- **交易号重复**：同一笔转账在付款方与收款方两份明细里交易号相同、但「用户方」不同；
  R5 按「订单号 + 用户方 + 方向」判重，不会误删两侧记录。
- **真实样本实测**（2 份账户明细 / 8,739 行原始记录 / 7 个账号 ID → 5 个姓名）：清洗后入表 8,057 行、1,438 个主体；
  支出 6,764,644.44 元 / 收入 3,725,731.70 元；与 97 个微信账单（64,310 行）合并后 72,367 行，`来源` 列区分正确。

## 大数据量下的表现（实测 97 个微信账单 + 2 份支付宝账户明细）

| 环节 | 结果 |
| --- | --- |
| A 导入与清洗（微信） | 97 个文件（31 个有数据、66 个仅表头，共 17.1 万行原始记录）→ 清洗后 64,310 行，约 3.4 s，`01_统一流水.tsv` 约 10.0 MB |
| A 导入与清洗（支付宝） | 2 个文件（8,739 行）→ 入表 8,057 行 / 1,438 主体，不到 1 s，`01_统一流水_支付宝.tsv` 约 1.4 MB |
| B 多来源合并 | 微信 64,310 + 支付宝 8,057 → 72,367 行（`来源` 列区分），`02_合并流水.tsv` 约 11.5 MB |
| C 总表与透视表 | 合并后 72,367 行，约 9 s → `03_流水总表.xlsx` 5.7 MB + csv 11.5 MB + `03_数据透视表.xlsx` 0.6 MB |
| D 资金流向图 | 合并后 6,762 主体 / 8,612 通道，约 7 s，HTML 约 2.0 MB |
| D 汇总件 + 人物关系图名单 | `03_数据透视表.xlsx`（10,195 行）→ 20 人名单、只看名单内双方往来 → 67 行 / 19 主体 / 20 通道，0.4 s，HTML 约 0.07 MB |
| D 汇总件 + 放宽口径 | 同一 20 人名单改为「含名单外的直接对手」→ 8,481 行 / 5,634 主体 / 7,183 通道，1.0 s，HTML 约 1.7 MB |

主体规模很大时功能 D 会自动降级，避免卡顿（页面里也会提示）：

- **布局**：主体数 > 499 时不再使用 networkx 的力导向布局（该规模会走 scipy 稀疏矩阵，
  而套件不依赖 scipy），改用按资金流量强度排序的黄金角螺旋布局——枢纽靠近圆心、结果可复现。
- **名字**：主体数 > 500 时不再逐个绘制名字（会糊成一片且每帧数千次绘制很卡），
  点击某个主体后只显示它的关联主体名字，未选中时用悬浮提示看名字。
- **一致性明细**：真实数据下不一致可能上万条，页面与报告只列出差异最大的前 200 处，
  统计口径（处数、差异合计）仍按全量计算。

## 常见问题

**Q：主界面能打开，但点任意一个功能都弹「打开失败 / No module named 'pandas'」。**

说明启动用的 Python 不是装了依赖的那一个。本套件依赖 pandas / networkx / openpyxl：
主界面本身只用标准库（tkinter），所以能正常显示；一旦进入功能才会 import 依赖，于是每个卡片都报同一个错。

- 查看当前用的是哪个解释器：命令行运行 `python -c "import sys; print(sys.executable)"`。
- 用装好依赖的解释器运行（本机 Python 3.13 线已装好）：`py -3.13 main.py`
- 或给当前解释器补装依赖：`"<该解释器的 python.exe>" -m pip install -r requirements.txt`
  （若是 Python 3.8 / Win7 线，请用 `pandas==2.0.3 networkx==3.1 openpyxl==3.1.2 xlrd==2.0.1`，
  不要装 pandas 3.x / networkx 3.6——它们不支持 3.8。）
- 打开功能时若缺依赖，弹窗会直接给出上面这些处理办法，不用逐个卡片去猜。

**Q：双击 `main.py` 打不开或一闪而过？** 用 `python main.py`（或 `py -3.13 main.py`）从命令行运行即可看到完整报错。

**Q：功能 A 报「没有可用的有效数据（N 行原始记录全部被清洗规则过滤）」？**

先看同目录的 `01_清洗报告.txt`：程序会把「过滤前多少行、R1/R2/R5/R7 各过滤多少行、实际读到的
借贷类型取值 top8」都写进去。常见原因是方向列取值不在支持范围内（当前支持
`支出/支/出/借` 与 `收入/收/入/贷`）或账单被判定为无数据行（只有表头）。
把报告内容发出来即可定位是否需要支持新的导出格式。

**Q：输入文件编码五花八门（ANSI/GBK、GB18030、UTF-16、带 BOM），会不会读乱？**

不会。v2.0.4 起所有文本读取都走同一条**严格解码链**：先按 BOM 判定，再依次严格尝试
`utf-8-sig → gb18030（GBK/GB2312 的超集）→ utf-16`，第一个成功的编码就用；只有全部失败才用
`utf-8 + errors='replace'` 兜底并打 `[WARN]`。每个文件都会在「运行日志.txt」里打印真实编码与行数：

```text
[INFO] 读取 D:\...\TenpayTrades.txt (编码: gb18030, 行数: 1234)
[INFO] 03_流水总表.xlsx → shape=(72368, 15) 列名=['用户ID', '用户方', ...]
```

以前用 `errors='replace'` 兜底，会把 ANSI 文件当成「看起来成功的乱码 UTF-8」读进来，
表头字段名与数据错位，最终在 pandas 分组阶段报
`InvalidIndexError: Reindexing only valid with uniquely valued Index objects`。

**Q：仍然报 `InvalidIndexError: Reindexing only valid with uniquely valued Index objects`？**

这条错误的直接含义是「索引或列名有重复值」，最常见来源是**重复列名**（表头行被粘贴了两遍、
或用 Excel 另存时列名重复）。v2.0.4 起在读取、归一（`normalize`）、合并、分组（功能 C/D）四处都加了防御：
重复列名按首次出现保留、重复索引自动 `reset_index(drop=True)`，并写
`[WARN] 检测到重复列名/索引，已重置`。若还报错，请把「运行日志.txt」发出来——
现在每个输入文件都会打印编码、`shape` 与完整列名，可直接定位是哪一个文件。

**Q：输出目录里的 `error_log.txt` 是什么？**

导入/清洗时**读取失败的文件不再静默跳过**：明细（文件全路径 + 失败原因）写进输出目录的
`error_log.txt`（UTF-8），同时终端与「运行日志.txt」打 `[ERROR]`，完成弹窗也会提示
「N 个文件读取/解析失败（未计入本批）」并多出一个「错误明细」按钮。
整批文件里个别坏文件不会影响其余文件继续导入。

**Q：总表里「交易时间 / 订单号 / 来源」等列整列空白？**

不是总表生成环节丢列，而是**输入流水本身就没有这些列**。功能 A 的「选择需要写入的列」里没勾的列
不会写进 `01_统一流水.tsv`；功能 B 合并时按契约把缺的列补齐、功能 C 读进来也只能补空串，
于是 `02_合并流水.tsv` 与 `03_流水总表.xlsx` 里这些列「列头在、值全空」。
v2.0.5 起功能 B（合并）和功能 C（总表）都会检查「交易时间 / 订单号 / 来源 / 交易类型 / 说明」是否整列为空，
在「运行日志.txt」打 `[WARN] 合并结果里这些列整列为空：…`（或 `输入里这些列整列为空：…`），
`02_合并说明.txt` 与完成弹窗里也会提示。
解决办法：回功能 A 重新导入并勾选这些列（`用户ID` / `对手方ID` 自 2.0.2 起强制保留、无需手动勾），
得到 14~15 列的 `01_统一流水.tsv` 后，再走一次合并与总表即可。

**Q：tsv 里明明有「交易时间」这一列，为什么总表里是空的？**

两种可能，日志里都能看到：

1. **那一列只有列头、值全空**（最常见）：合并时按统一格式补列造成的，`运行日志.txt` 会有
   `[WARN] 合并结果里这些列整列为空：交易时间、…` —— 回功能 A 勾选后重新导入即可。
2. **列名带了看不见的字符**（尾部空格、零宽空格、全角空格等，常见于 Excel 另存或复制粘贴）：
   以前这种列名匹配不上标准列名，原列会被丢弃、再补一列空的，于是数据「凭空消失」。
   v2.0.5 起读取时会先做列名归一，日志打
   `[WARN] 列名含不可见字符或多余空白，已按标准列名归一：交易时间  → 交易时间`；
   若列名完全是别的写法（如 `交易时间(UTC+8)`），会打
   `[WARN] 丢弃无法识别的列（列名与标准列名不一致）：…`，照着改成标准列名即可。

**Q：功能 D 在几千个主体时提示「已改用快速近似布局」？**

正常降级，不是错误：networkx 的力导向布局在节点数 ≥ 500 时会要求 scipy，套件不引入这个依赖，
因此改用快速近似布局。布局、名字与一致性明细的降级规则见上文「大数据量下的表现」。

**Q：功能 D 怎么给流水加上「角色」并只看某一类角色？**

打开 `03_数据透视表.xlsx`，在 **人物关系图** 表里按 `序号 | 姓名 | 角色` 填写（姓名与流水里的名字一致即可），
**数据透视表** 的 `用户侧角色` / `对手侧角色` 两列是 VLOOKUP 公式，会自动带出角色；未填写的显示 `#N/A`。
随后选中表头 → 数据 → 筛选，即可只保留某一类角色。工作簿已设置「打开时重算」，不需要手动 F9。

在功能 D 里同样可用：选到 `03_数据透视表.xlsx` 后点 **「载入「人物关系图」人物」** 一次带入全部已填姓名，
或点 **「选择关注的人…」** 第一段按角色整组勾选（读的也是「人物关系图」表）。

**Q：功能 D 里数据太多、图看不清怎么办？**

两种筛选口径，二选一：

- **只看名单内双方的往来（默认，推荐）**：用户方和客户方**都要在名单里**，只保留关注的人彼此之间的通道，
  最适合研判团伙内部往来，数据量能小两三个数量级；
- **保留选中人物的往来（含直接对手）**：选中的人及其所有对手都留在图里，适合看某个人的资金网络，但图会大很多。

还可以叠加「金额下限」和「日期范围」把小额、无关时段的记录去掉。窗口里会实时显示当前筛选条件，
生成完成后弹窗与 `运行日志.txt` 里也会写清「筛选前多少行 → 筛选后多少行」。

**Q：功能 D 直接选 `03_数据透视表.xlsx` 会报错吗？**

不会（v2.0.0v4 起它就是**推荐输入**）：透视表虽然只有 `主体 ↔ 对手` 的合计金额与笔数，
但这正是流向图的边数据。程序按列名认出「数据透视表」表（`用户方 | 用户侧角色 | 支出/收入 | 客户方 |
对手侧角色 | 求和项:金额(元) | 笔数`）后直接构图，不再把它当逐笔明细解析。
（v2.0.3 起 `tools/flow/analyze.py` 也改为**按列名**取数，列顺序怎么排都不受影响；
此前按「前 4 列列位」读取，列顺序一变就会把角色列当方向、客户方当金额，整表判为空白行并报
`没有可用的有效数据。`）汇总件没有逐笔时间，因此「日期范围」对它无效——窗口状态行与 `运行日志.txt` 会提示。

**Q：支付宝账户明细导入后「对手方接收金额 / 对手侧银行名称」两列不见了？**

正常：这两列是财付通账单专有字段，支付宝没有 → 整列为空，按「空列自动省略」不写入产物。
功能 B 合并时会按统一契约把缺列补齐（为空），与微信流水一起使用不受影响。

**Q：支付宝账单里「收/支=其它」的那些行去哪了？**

真实样本里 225 行「其它」全部是「余额宝-自动转入 / 余额宝-转出到余额」且对手方就是本人，属于自账户划转，
按 R2 过滤；`01_清洗报告_支付宝.txt` 第五节会列出这些行的构成，便于核对是否漏了业务流水。
